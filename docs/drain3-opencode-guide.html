Drain3 log summaries for OpenCode

Repetitive log output is the most expensive thing a coding agent reads. This guide installs the Drain3 template miner, wraps it as a one-command summarizer, hooks it into OpenCode so the model sees nine templates with counts instead of eight hundred lines, and puts a browser dashboard on top so you can see what it saved. Every step was run and verified on a real machine; the numbers below are from that run.

What Drain does

Drain parses each log line into a template (the fixed words) and parameters (the parts that vary), online, in one pass, using a fixed-depth parse tree. It runs at hundreds of thousands of lines per second on a CPU. Given masks for the fields that always vary, it turns this:

Word-level compressors such as LLMLingua-2 are the wrong tool for this: they drop PIDs, IP octets and keywords because those look like low-information tokens. Template mining keeps every distinct value and only removes repetition.

1

Install uv and Drain3

Nothing here needs sudo. uv manages Python and the virtual environment; Drain3 is a pure-Python package. tiktoken is optional: with it the dashboard reports exact token counts, without it a regex estimate that is within about two percent on logs.

Check it: uv run python -c "import drain3; print(drain3.__file__)" should print a path under ~/logsum/.venv.

2

Write the summarizer

Save this as ~/logsum/logsum.py. It reads a log on stdin and prints templates with counts and line ranges. Three rules make it safe to put in front of every log command: input of 40 lines or fewer passes through untouched, templates seen three times or fewer are printed verbatim because rare lines are the signal, and the last ten lines are always shown verbatim because the newest line is usually the one that matters.

It also records every call to ~/.local/share/logsum/stats.jsonl for the dashboard in step 7. The record is written by a forked, detached child after the output has been flushed, so token counting never delays the agent. Two environment variables let callers attribute the call: LOGSUM_AGENT and LOGSUM_CMD_B64, the command in base64 so no quoting can break it.

The masks are the whole game. Without the IP and PID masks, the same 800-line log fragments into hundreds of clusters and the summary is useless. If your logs carry request ids, trace ids or usernames, add a mask for each before anything else.
3

Expose it as a command and test it alone

The wrapper calls the venv's Python directly. Going through uv run on every tool call would add a dependency check to the hot path.

Make a realistic test log. This generator writes 800 lines with nine message shapes, including errors whose parameters vary, which is what a real service log looks like from the model's point of view.

Expected: the three-line input echoes back as is, the 800-line log returns in about 0.2 seconds as the header line, nine templates, and the tail, and the stats file has one JSON line with "tok_in": 25827, "tok_out": 875. If you have journal access (adm group), journalctl -n 1000 --no-pager | logsum is a good second test on real data.

4

Install OpenCode and give it a model

PATH is on you. The installer drops the binary in ~/.opencode/bin and, at least in version 1.18, does not add that directory to any shell rc file. If a new terminal says "opencode: command not found", this is why. The same line covers ~/.local/bin, where uv and the logsum command live.

OpenCode needs a provider. Either run opencode auth login and follow the prompts, or export a key before starting it. Keys in a .env file in the project directory are loaded automatically.

Organization-scoped Anthropic keys fail with "this request must include the anthropic-workspace-id header". Either use a workspace-scoped key, or add the header in ~/.config/opencode/opencode.json under provider.anthropic.options.headers.
5

Add the plugin

OpenCode loads every file in ~/.config/opencode/plugins/ at startup. The plugin hooks tool.execute.after, which runs after a tool has finished and lets you rewrite the text handed back to the model. The command itself is never changed, so exit codes and side effects are exactly what the agent asked for.

It only acts when the bash command reads a log (journalctl, dmesg, docker or kubectl logs, or cat/tail/head on a .log file, /var/log, syslog, or a logs/ directory) or when the read tool opens a .log file. Commands already piped into grep or awk are left alone, as is anything containing nologsum. It passes LOGSUM_AGENT=opencode and the command to the summarizer so the dashboard can attribute the savings. Any failure falls back to the raw output and writes a line to an audit log.

6

Run the end-to-end test

Use a throwaway project so the agent cannot touch anything real, and run OpenCode headless with --auto so it does not stop to ask permission for the bash call.

Three things prove it worked. The audit log has one line for the bash call showing the size reduction. The answer quotes the template counts rather than guessing from raw lines. And the session export contains the summary header where the tool result used to be:

7

Put a statistics dashboard in the browser

The summarizer already writes one JSON line per call. The dashboard is a single Python file with no dependencies beyond the standard library: it serves a page at http://localhost:8765 and a JSON endpoint at /api/stats, re-reads the stats file whenever it changes, and refreshes itself every 15 seconds.

What you see, top to bottom:

  • Five tiles. Calls (summarized versus passed through), tokens before, tokens after, percent saved, and the estimated cost saved at a price per million input tokens you can edit. The price is remembered in the browser.
  • Tokens per day. One bar per day, blue for what the model actually read, orange stacked on top for what logsum removed. Hover a day for the numbers; the "Show as table" button gives the same data as text.
  • Latest summary, how Drain3 saw it. The five most frequent templates of the most recent call, with counts and the wildcards highlighted. This is the quickest way to check that the masks fit your logs.
  • By agent. One row per caller, so you can compare what OpenCode and any other agent saved.
  • Recent calls. The last 60 calls with command, lines, tokens, percent saved and processing time. Each row expands to its templates.

Save the server as ~/logsum/logsum_stats.py:

Show logsum_stats.py (server plus the dashboard page, about 170 lines)

Then give it a wrapper and run it as a user service, so it starts with the machine and restarts if it dies. No sudo is needed for systemctl --user.

Open http://localhost:8765 in a browser. If the machine is remote, keep the server on 127.0.0.1 and tunnel: ssh -L 8765:127.0.0.1:8765 user@host. Binding to 0.0.0.0 exposes your command history to the network, so only do that behind a firewall you trust.

Docker instead of systemd. The repository also ships a container that runs the summarizer as a warm HTTP service together with the dashboard: scripts/docker-up.sh builds it, starts it on port 8765, and installs a small logsum client that POSTs to /summarize and falls back to passthrough if the container is down. A call costs about 35 ms instead of 200 ms because Drain3 and tiktoken stay loaded. Stats live in a named volume; the audit logs are mounted read-only.
Reading the stats file directly. It is plain JSON lines, so jq works too: jq -s 'map(select(.passthrough|not)) | {calls: length, before: map(.tok_in)|add, after: map(.tok_out)|add}' ~/.local/share/logsum/stats.jsonl. To start over, delete the file; the dashboard shows an empty state until the next call.

Tuning and limits

  • Thresholds. PASSTHROUGH_LINES decides when summarizing starts, RARE_MAX how rare a template must be to stay verbatim, TAIL_LINES how much recency to keep. The defaults were chosen so a 300-line read costs about 30 lines.
  • Opting out. Any command containing nologsum (for example tail -n 500 app.log # nologsum) is passed through, and the summary header tells the model so. Commands that already filter with grep, awk or jq are never touched. Set LOGSUM_NOSTATS=1 to stop recording.
  • Multi-line records. Drain is line-based. Java or Python stack traces become one template per frame. Group them into one record per exception before mining, or the summary hides the trace.
  • New masks. Add a regex and a name to MASKS; earlier entries win, so put the more specific pattern first, as with IP:PORT before IP. The "Latest summary" panel on the dashboard shows immediately whether a new mask took.
  • Both files are one system. Edit ~/logsum/logsum.py and every agent that calls logsum picks up the change on its next tool call. No restart is needed.
  • Other agents. Anything that can run a shell pipeline can use it. Claude Code, for instance, cannot modify tool output after the fact, so there the same summarizer is wired as a PreToolUse hook that rewrites the command to … | env LOGSUM_AGENT=claude-code logsum. The dashboard then shows both agents side by side.

Removing it

OpenCode itself is removed with opencode uninstall.
